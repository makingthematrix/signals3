# Behaviors Refactoring Plan

Written on branch `actors`, HEAD `8c70bb9` ("refactoring behaviors -- in progress").
Companion analysis notes: this is the full plan for finishing the refactoring described below.

**Commit policy (per the maintainer):** no commits until the test suite is green again - i.e. not
before P8/P9. Every phase lands in the working tree and is verified with `sbt compile` only; all
phases P1-P9 are committed once `sbt test` passes.

## Goal

Every behavior function must be registered in the **`Behaviors` object** - the behavior library -
either under a caller-provided identifier or under one generated by `IdGenerator`. Lifecycle events
(`onInit`, `onPause`, `onUnpause`, `onClose`, `onBeat`) and actor behaviors hold **only identifiers**.
The function is fetched from `Behaviors` **only when the behavior is about to be triggered**.

## The behavioral model

| Kind | Function type | Registry | Used for |
|------|---------------|----------|----------|
| `Beh`  | `() => Any`                            | `Behaviors` (separate map) | `onInit`, `onPause`, `onUnpause`, `onClose` |
| `Fail` | `Throwable => Any`                     | `Behaviors` (separate map) | failure handlers of all lifecycle events |
| `TBeh[Msg, State]` (function alias `TF`) | `MutableActor[Msg, State] => Any` | `Behaviors` (shared with PBeh) | `onBeat` |
| `PBeh[Msg, State]` (function alias `PF`) | `PartialFunction[(Msg, MutableActor[Msg, State]), Option[Msg]]` | `Behaviors` (shared with TBeh) | actor message behaviors |

Identifiers are **globally unique across all kinds** (`Beh`, `Fail`, `TBeh`, `PBeh`): no two behaviors in
the whole system share an id. Rationale: ids are used as debugging handles, so collisions are confusing.
The four kinds are stored in separate maps, and every `register*` method checks all of them (enforced in P1).

### P1. `Behaviors` object - settle the registry API - **DONE**

Implementation notes (done on top of 8c70bb9): added a private `idTaken(id)` helper that checks all
four registries; `registerBeh`, `registerFail`, `registerPBeh`, `registerTBeh` all refuse a taken id
through it; the class scaladoc, the two `registerP|TBeh` `@return` docs, the `unregister` doc, and the
`TF` doc (five events → onBeat only) were updated. `sbt compile` green; test churn deferred to P8 as
planned (the ActorBehaviorsSpec "Beh and Fail share an id" reversal + `unregister` rename there).

**[Resolved D1]** Keep the unified `unregister` (no split into `unregisterBeh`/`unregisterFail`).
Identifiers are **globally unique across all behavior kinds** (`Beh`, `Fail`, `TBeh`, `PBeh`) - on purpose:
ids double as debugging handles, so two behaviors anywhere in the system must not share one.

Consequences:

- Fix the id-space asymmetry (bug 5): `registerPBeh`/`registerTBeh` currently refuse ids taken by a `Beh`
  but not by a `Fail`. Under the global-uniqueness rule, **every** `register*` method must check all four
  registries (`behs`, `fails`, `pbehs`, `tbehs`) before accepting an id.
- Update the `Behaviors` scaladoc ("Beh and Fail each have their own registry, so ids are unique within
  a kind") to state the global uniqueness rule.
- Update the `TF` scaladoc ("all five lifecycle events" → onBeat only).

### P2. `priv.BehaviorRegistry` - ids only - **DONE** (P3 folded in)

Implementation notes: the registry now stores only ids (`ArrayBuffer[String]` x2) plus `ownedBehs`/

(constructor flag; used by `Init` and `Close`), owned ids (behaviors and fails) are unregistered from
`Behaviors`. The three traits route through this with no breaking API change (`Unit` → `String`
widening on the registration methods). `reset()` bug fixed. `priv.Closeability` simplified: its
private closeable list and the `onClose(beh)` override are gone - the compound's inherited registry
plus `runOnClose()` replace them, so one-shot cleanup covers compound closeables as well. **P3 done
along the way:** the `"Unpause)"` typo and the `onCloseFailed` finality/typing alignment. The stale
`Beh` import in `CloseableGeneratorStream` was removed. Verified with `sbt compile` (clean; only the
6 pre-existing warnings remain) plus a temporary smoke `main` covering: one-shot close/init cleanup,
failed-close rollback and retry, silent skip of missing ids, recurring pause persistence, global id
uniqueness rejection, user-supplied shared-id survival, and the compound wiring - all passed; the
smoke file was deleted afterwards.

- `behs`/`fails` become `ArrayBuffer[String]` - plus an `ownedIds: Set[String]` of ids whose functions
  were **auto-registered by the sugar** (see the "Id ownership and cleanup" section).
- `add(body: => Any)` → `Behaviors.registerF(() => body)`, store and **return** the generated id (owned) - see D3.
- `add(id, f)` → `Behaviors.registerBeh(id -> f)` (global uniqueness now enforced) + store and return the
  id (not owned: the user supplied it, they may share it across instances).
- Same for `addFailId` via `registerFailCase` (owned) and `registerFail` (not owned).
- **[Resolved D2]** `run()` resolves each id via `Behaviors.getBeh`/`getFail` **at trigger time**; a missing id
  (registered as an id here, but its function was unregistered from `Behaviors` in the meantime) is
  **skipped as a no-op** - it neither fails the event nor runs the `Fail` behaviors of other ids.
- **[Resolved D3]** Cleanup: after a **successful** run of a one-shot registry - `Init` and `Close` only -
  unregister the registry's **owned** ids (behaviors and fails) from `Behaviors`. A failed run keeps them:
  both events are retryable (`initialize()` rolls back, `closeAndCheck()` rolls back). Recurring registries
  (`Pause`, `Unpause`) never auto-unregister. Never unregister **user-supplied** ids - the same Beh id may
  be registered with several actors via `onInit`, and one actor's successful init must not remove the
  function under the others.
- Fix `reset()` (bug 1).
- Update `priv/Closeability` to store ids and resolve at call time.

With this, `CanBeInitialized`, `CanBePaused`, `CanBeClosed` inherit the fix with **no breaking API change**:
all overloads (Beh tuple, by-name, (id, f), `*ById`) keep their signatures; the ones that used to return
`Unit` now return the id (`String`) - a source-compatible widening (callers that ignore the result are
unaffected).

### P5. `ActorImpl` - behaviors to ids - **DONE**

Implementation notes (on top of 2442d33, after P4): `behaviors` is now `List[String]` plus a

`buildActor` keeps the invalid-id diagnostic against `getPBeh` and wires `validIds` directly.
`spawn` sites in `ActorImpl` and `ActorSystem` pass `this.behaviors` (already ids). Verified by an
18-check smoke: builder wiring, invalid-id skip, runtime `SetBehavior`/`RemoveBehavior` (precedence,
double-add and unknown-id rejections, function surviving in `Behaviors`), the named-behavior path,
mid-flight unregister skip, one pf shared by two actors, and spawn inheritance of behavior ids.
Smoke file deleted after.

- Replace `behaviors: List[PBeh]` + `behMap` with an ordered id list (+ a HashSet for containment checks).
- `addBehavior(id)`: check the id exists in `Behaviors` (respond `InvalidId` otherwise), append the id -
  never cache the function.
- `addBehaviors` becomes id-based; `removeBehavior` filters ids.
- **[Resolved D2]** `onMessage` resolves the pf fresh from `Behaviors.getPBeh[Msg, State]` per processing; a

  path as an unhandled message - the ask promise then fails with `FailToRespond`, as with any ignored message.
- For a **named** behavior requested via a non-empty `pbehId` in the message entry, `RemoveBehavior` + a later

- `spawn`: drop `this.behaviors.map(_.id)` - the list already holds ids.

SystemMsg type-casting note: after P5 the only unchecked casts are in `Behaviors.getPBeh`/`getTBeh`,

## Id ownership and cleanup (D3, **revised by the maintainer after P2**)

The maintainer tightened the rule: **no implicit cleanup at all**.

1. A behavior function is registered explicitly in `Behaviors` (`registerBeh`, `registerFail`,
   `registerPBeh`, `registerTBeh` - with a caller-given id, or via the sugar with a generated id
   which those methods return), and then attached to an event by id (`onEVENTId`). Functions
   registered this way are never auto-unregistered - the user may share ids between objects.
2. The event traits also offer by-name registration (`onEVENT(body)`) - registers with a generated id
   and returns it; the function stays in `Behaviors` until manually unregistered.
3. **The only automatic unregistration**: an explicit `onEVENTOneShot(body): Unit` (offered for the
   one-time events - onInit, onClose - and their fail handlers). After a **successful** run of the
   event, the one-shot's function is unregistered from `Behaviors`. A failed (retryable) run keeps
   it for the retry.
4. Full `Beh`/`TBeh`/`PBeh`/`Fail` registration is done explicitly in `Behaviors`, never through
   `BehaviorRegistry`. The registry either attaches an existing id (`addId`) or generates a whole new
   behavior (`add`, `addOneShot`, and the fail variants).
5. New `resetOnEVENT` methods (`resetOnInit`, `resetOnClose`, `resetOnPause`, `resetOnUnpause`) sever
   an event from all its behaviors; the functions stay in `Behaviors`.
6. Renames in this revision: `onEVENTById` -> `onEVENTId`, `onEVENTFailedById` -> `onEVENTFailedId`
   (the last `onPauseById` holdout was renamed to `onPause` in the follow-up pass); the `Beh`/`Fail`
   tuple and `(id, f)` registration overloads were removed from the traits. Confirmed intentional by
   the maintainer: no one-shot forms for the recurring `Pause`/`Unpause` events, and the `resetOnEVENT`
   hooks are groundwork. P8 note from the maintainer: one-shots (whose ids are unobservable - `Unit`)
   are to be tested behaviorally - add a behavior, test it works, sever/reset it with `resetOnEVENT`,
   test it does not work anymore.
7. **Ordering convention (after P5) - ABANDONED (decision by the maintainer):** behavior ids are now
   kept in `mutable.HashSet`s in `BehaviorRegistry` and `ActorBuilder`. An id is present at most once
   (duplicate attaches are silently ignored - this also resolved the old point 5), and there is NO
   guaranteed relative run order among behaviors configured through the builder or attached to a
   lifecycle registry. All order-tracking bookkeeping (newest-first lists, reversed attaches,
   dedup checks) was removed. **Still ordered, out of scope of this decision:** `ActorImpl.behaviors`
   (a `List` - a runtime `SetBehavior` through a system message still runs first in the message
   dispatch and can take over) and `MutableActor._onBeat` (a `List`). The maintainer may want to
   unify them later. **P8 must watch out for:** order-sensitive test expectations (`createWithBehaviors`
   docs, behavior-takeover assertions for builder-configured behaviors - takeover via runtime
   `SetBehavior` is preserved).

Consequences for later phases:
- P5-P7: library-internal by-name wiring that is genuinely run-once (e.g. `ActorImpl`'s `onInit {...}`,
  `Closeability`'s per-source close wiring, `isClosedSignal`'s `onClose(signal.set())`) should use the
  OneShot variants - with the care that *Failed* handlers must NOT be one-shot (failures are retryable).
- Memory: wiring registered with plain `onEVENT` stays in `Behaviors` forever - accepted.
- P8: one-shot coverage tests must exercise `BehaviorRegistry` directly (one-shots return `Unit`,
  so their cleanup is unobservable through the public API).

| D6 | Hardening: store Msg/State ClassTags at registration, verify at `getPBeh`/`getTBeh` | **Deferred**: revisit after the refactoring is done. Until then the trust-based unchecked cast stands; misuse surfaces as a ClassCastException at processing time |

## Notes (decisions to revisit)

- **Partial behaviors are OUT of this refactoring (decision by the maintainer).** `Spawn.behaviors`
  stays a `List[String]` and `ActorImpl.behaviors`/`behSet` keeps its `List` (+prepend, runtime
  `SetBehavior` takeover semantics) - they have not been converted to sets. **Future plan (the
  maintainer):** a very different refactoring of partial behaviors is intended later - to allow
  only ONE partial behavior at a time per actor (replacing the current lists/chains of partial
  behaviors and their dispatch precedence entirely). Until then, they stay as-is - both in the actor
  and in `Spawn`.

- **Sugar naming (settled by the maintainer, after P6):** `addBehaviorPF`/`addBehaviorPFs` for
  message behaviors, and for every lifecycle event a function variant `withOnEVENTF(f)` plus a
  collection variant `withOnEVENTFs(fs)` - init takes `TF` functions (registered at build time,
  closing over the built actor), pause/unpause/close take `() => Any` (registered immediately through
  `Behaviors.registerF`, with the `onPause`/`onUnpause`/`onClose` prefixes; ids readable through the
  id fields). The P6 `withOnInit(f: TF)` overload was RENAMED to `withOnInitF` by this rule
  (`withOnInit(Iterable[String])` stays for ids). `addOnBeatTF` keeps its TF overload as is.
  In-group order: the first function of a collection runs first among them; a later registration
  runs before earlier ones (the global prepend convention).

- **D1 (resolved for now, revisit later):** the `unregister` API stays unified; identifiers are globally
  unique across all behavior kinds. Register on debuggability - ids that appear in logs, crash traces,
  and serialized state must never be ambiguous. If the global-uniqueness rule ever gets relaxed,
  revisit which of the four registries a `register*` call must check.
- **D2 (resolved for now, revisit later):** a missing id at trigger time is a silent no-op - skipped in
  lifecycle `run()`s (P2, P4) and `NoResponse` in message processing (P5). The alternative on the table
  was failing the event/promise; revisit if silent skipping turns out to mask bugs, e.g. behaviors
  unregistered by one actor taking effect on another sharing the id. A missing id can only happen
  through `Behaviors.unregister` between registration and trigger - until then, ids are validated at
  registration.
- **D3 (resolved):** owned-id cleanup for one-shot events + ids returned from utility methods - see the
  "Id ownership and cleanup" section. `resetOnBeat()` and `shutdown()` deliberately do **not**
  unregister (the user may re-use identifiers elsewhere). Revisit trigger: if a profile of a long-running
  app still shows `Behaviors` growth, the drivers are beat/pause/unpause and closed actors' behavior ids -
  by design; the escape hatch is the user calling `Behaviors.unregister` with the saved ids.
- **TF adaptation (final semantics, after the maintainer's MutableActor refactor + fixes):** every
  lifecycle event is `Beh`-based (`() => Any`) at the actor - including `onBeat`, which now routes
  through a plain `BehaviorRegistry("Beat")` in `MutableActor` instead of a TBeh registry. Actor-taking
  functions (`TF`) are supported through dedicated adapter methods on the actor -
  `onInitTF`/`onPauseTF`/`onUnpauseTF`/`onCloseTF`/`onBeatTF` (+ the `OneShotTF` variants of init and
  close) - which adapt `tf(this)` at event time, passing the actor itself. Consequences:
  - `MutableActor.onBeat` takes an explicit `() => Any` (not by-name), so an actor-taking lambda
    passed to it is a compile error, not a silent no-op.
  - In the BUILDER, `addOnBeatTF`/`TFs` keep the functions in a `beatFuncs` backlog and adapt them
    with the built actor at build time - so their ids are NOT visible on the builder
    (documented; register in `Behaviors` and use `addOnBeats` if the id is needed).
  - `SystemMsg.AddOnBeat(tbehId)`: `ActorImpl.addOnBeat` resolves the tbeh via `getTBeh[Msg, State]`
    (the single auditable trust-based cast) and adapts it with `this` - attaching a generated
    `Beh`, NOT the tbeh id itself, to the beat registry. Raw tbeh ids cannot be attached by id
    (`onBeat` validates only Beh ids).
  - (Asymmetry noted for a later decision: the builder has no `addOnInitTF`.)
- **D6 (deferred):** ClassTag hardening of the PBeh/TBeh registries - come back to this once the
  refactoring is done. Concretely: store the `ClassTag`s of `Msg`/`State` alongside each registered
  function and have `getPBeh[Msg, State]`/`getTBeh[Msg, State]` verify them at retrieval, turning the
  current trust-based unchecked cast (misuse = ClassCastException at processing time) into a typed
  `false`/`None` result. Nothing in the plan depends on it.

## Risks

- **Growth of `Behaviors`** - largely mitigated by D3: the dominant driver was streams'/signals'
  `onClose` bodies (one-shot → auto-cleaned after a successful close). Remaining drivers, accepted by
  design: ids of recurring events (pause/unpause/beat) and behavior ids of closed actors, since
  identifiers may be re-used elsewhere and are therefore never auto-unregistered (see the "Id ownership
  and cleanup" rules). This interacts with the intent of using `Behaviors` as a persistent, id-addressable
  behavior dictionary (see the notes in `ActorSystem_old.md` about serializing behavior ids); that
  persistence intent is exactly why the user-facing cleanup is manual and id-based.
- **Runtime cost**: one HashMap lookup per trigger/processing instead of the cached function - negligible.
- **Erased types**: `getPBeh[Msg, State]`/`getTBeh[Msg, State]` are resolved with the receiving actor's
  type parameters on trust; a cross-typed misuse fails at processing time, not at registration.
